Liftlyf Technical Documentation

Engineering the Liftlyf platform.

Liftlyf is a full-stack workout tracking application. The project combines native Android development, local data persistence, HTTP-based APIs, backend services, authentication, relational databases, containerization and cloud deployment.

01. Project Overview

Liftlyf is designed around a simple product goal: provide users with a focused way to record workouts and maintain a history of their training.

From an engineering perspective, the project extends beyond the Android application itself. It includes a client application, backend services, persistent data storage and hosted infrastructure.

02. System Architecture

Liftlyf follows a distributed client-server architecture. The Android application acts as the client, while the backend provides server-side services and persistent data access.

The main architectural separation is intentional: presentation, client-side data handling, network communication, business logic and persistent storage should remain independently maintainable.

03. Android Application

The Android client is built using Kotlin and Jetpack Compose. Jetpack Compose provides a declarative approach to constructing the application's user interface.

Presentation Layer

The presentation layer is responsible for displaying application state and receiving user interactions. Screens represent the user interface for features such as workout tracking, exercise management and workout history.

State Management

Application state should flow in a predictable direction: user interaction produces an event, application logic processes that event, the underlying data changes and the UI reflects the updated state.

User Interaction ↓ UI Event ↓ Application Logic ↓ Repository / Data Source ↓ Local Storage or Backend ↓ Updated Application State ↓ UI Recomposition

Local Persistence

Room provides structured local persistence on Android. A local database allows application data to be stored on the device rather than existing only in temporary memory.

Jetpack Compose

Declarative UI framework responsible for rendering application screens from state.

Room

Provides an abstraction over SQLite for structured local application data.

Retrofit

Provides typed HTTP communication between the Android client and backend APIs.

Kotlin

Primary language for Android application development and application logic.

04. Offline-First Data & Synchronization

Liftlyf uses a local-first architecture for workout data. The Android application does not depend on a network request every time a user records a workout. Workout data is first written to the local Room database, allowing the application to remain responsive and usable without a continuous internet connection.

Local-First Workflow

User records workout data ↓ Android application processes the update ↓ Data is written to Room ↓ UI reads the updated local state ↓ Workout remains available on the device ↓ Synchronization process sends data to backend ↓ Spring Boot processes sync request ↓ PostgreSQL is updated

Room acts as the application's local data layer, while PostgreSQL provides persistent server-side storage. This separation allows the Android application to operate independently of immediate network availability.

Why Local-First?

  • Workout logging does not need to wait for a network request.
  • The UI can immediately reflect changes stored locally.
  • The application remains usable during temporary connectivity loss.
  • Network synchronization can occur independently of user interaction.
  • Remote storage provides a server-side copy of synchronized data.

05. Synchronization API

Synchronization between the Android application and the backend is performed through the API layer. The Android client communicates with the Liftlyf backend using Retrofit and HTTP-based requests.

Room Database ↓ Repository / Synchronization Logic ↓ Retrofit ↓ HTTP Request ↓ Liftlyf Sync API ↓ Spring Boot ↓ Service Layer ↓ Persistence Layer ↓ PostgreSQL ↓ Sync Response ↓ Android Application

Synchronization Responsibilities

The synchronization layer acts as a boundary between the local Android database and the remote backend. Instead of exposing the Room database directly to the server, the client sends structured API requests.

  • Collect local workout data that requires synchronization.
  • Serialize application data into API request objects.
  • Send synchronization requests using Retrofit.
  • Authenticate and validate requests at the backend.
  • Process incoming data through the backend service layer.
  • Persist synchronized data in PostgreSQL.
  • Return a response indicating the result of synchronization.

Conceptual Sync Request

Android ↓ POST / sync endpoint ↓ Authorization handled by Spring Security ↓ Request validated ↓ Controller receives synchronization request ↓ Service processes workout data ↓ PostgreSQL records created or updated ↓ Response returned to Android

The API acts as a synchronization boundary. The Android application communicates with the backend through structured request and response objects rather than directly accessing PostgreSQL.

05. API Layer

Communication between the Android application and backend is based on HTTP requests and REST-style APIs.

Request Lifecycle

Android Application ↓ Retrofit creates HTTP request ↓ Request reaches backend endpoint ↓ Spring Security processes request ↓ Controller receives valid request ↓ Service layer executes business logic ↓ Persistence layer interacts with PostgreSQL ↓ Backend creates response ↓ HTTP response returned to Android client

Separation of Responsibilities

  • Client: user interaction and presentation.
  • API layer: transport boundary between client and server.
  • Controller: request handling and endpoint coordination.
  • Service: business logic and domain operations.
  • Persistence: database interaction.

06. Backend Architecture

The Liftlyf backend is built using Spring Boot. Its role is to expose application services through APIs and provide a server-side boundary for business logic and persistent data access.

HTTP Request ↓ Spring Security Filter Chain ↓ Controller ↓ Service Layer ↓ Repository / Persistence Layer ↓ PostgreSQL ↓ Response DTO / HTTP Response

Controller Layer

Controllers define the API boundary. They receive requests, validate or map incoming data and delegate business operations to the service layer.

Service Layer

The service layer represents the natural location for server-side business logic. This keeps controllers focused on HTTP concerns rather than application rules.

Persistence Layer

Database access is separated from higher-level application logic. This separation improves maintainability and keeps SQL or persistence concerns isolated from API and business logic.

07. Authentication & Security

The backend uses Spring Security as the foundation for protecting application resources. JWT-based authentication provides a mechanism for authenticated clients to prove identity when calling protected endpoints.

Conceptual Authentication Flow

User authenticates ↓ Backend validates credentials ↓ Backend issues authentication token ↓ Client sends token with protected requests ↓ Backend security layer validates token ↓ Authenticated request continues
Implementation details such as token expiration, refresh-token support and the exact client-side storage mechanism should be documented according to the actual Liftlyf implementation rather than assumed.

Security Responsibilities

  • Authentication of users.
  • Protection of authenticated API endpoints.
  • Validation of authentication tokens.
  • Authorization rules where applicable.
  • Separation of public and protected resources.

08. Database Architecture

PostgreSQL is used as the backend relational database. Relational storage is suitable for structured application data and relationships between application entities.

Typical Data Relationships

User ↓ Workout ↓ Workout Exercise ↓ Exercise Sets Example logical relationship: User └── Workouts └── Exercises performed └── Individual sets / repetitions / weight

The exact schema should be treated as an implementation detail and should evolve with application requirements. The important architectural principle is maintaining clear ownership and relationships between persistent entities.

Local vs Server Storage

Room

Provides structured on-device storage for Android application data and local persistence.

PostgreSQL

Provides persistent relational storage for backend-managed application data.

Why Containerization?

  • Provides a consistent runtime environment.
  • Reduces differences between development and deployment environments.
  • Packages application dependencies with the application.
  • Simplifies deployment and replacement of backend versions.

Cloud Infrastructure

Hosting the backend on a cloud VM moves Liftlyf beyond a purely local development environment. The backend can run independently of the developer's local machine and serve remote application clients.

11. Engineering Decisions

Native Android Development

Kotlin and Jetpack Compose provide a modern native Android stack. This allows Liftlyf to use platform-native APIs while maintaining a declarative UI architecture.

Client-Server Separation

A dedicated backend prevents all application logic and persistence concerns from being embedded directly inside the mobile client. The client and server can therefore evolve independently.

Local Persistence

Using Room creates a structured approach to on-device data persistence and supports an architecture where application state does not depend exclusively on temporary memory.

Containerized Backend

Docker provides a reproducible runtime environment and makes the backend easier to package and deploy.

Cloud Hosting

Running the backend on Oracle Cloud introduces production-style infrastructure concerns such as server availability, networking, deployment and operational maintenance.
